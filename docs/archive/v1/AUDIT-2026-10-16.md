# Travel repo audit and target design (16 Oct 2026)

Scope: the `travel` repo as pushed to GitHub on 16 Oct 2026 (267 files, 8.4 MB tracked), the `trip-planner` skill, `_system/`, `publish.sh`, and the destination bucket list that currently lives in the Obsidian vault (`notes/Notes/life/travel/Location.md` and its `personal/` twin). Nothing in this document has been applied yet except where the change log at the end says so.

Verdict in one paragraph: the plans themselves are strong (the Patagonia and Rockies PLAN.md files are the best-structured documents in the repo), but the machinery around them has drifted. Seven trips are built through `_system`, three were lifted onto it, two are hand-written, and two have no plan at all. Photo and sun-time helpers are copied per trip instead of shared. `publish.sh` publishes 81 scripts, JSON and scratch files to the public site. Destination capture has no structure at all: it is a hand-maintained Obsidian callout list, duplicated in two folders, with no hierarchy below country, no coordinates and no source links. There are no hooks, no tests, and no pre-publish gate. The fixes below are ordered so the cheapest ones with the biggest effect come first.

### 1.4 Destination capture has no structure

What exists: `Location.md` in the Obsidian vault, a flat list of `> [!tip]-` callouts grouped by country, duplicated byte-for-byte (apart from wiki-link paths) in `life/travel/` and `personal/travel/`. Twenty-six entries after this week's additions.

Problems found while adding entries this week:

- No level below country. "Canada" now holds a canyon, a ski-resort lookout, five individual trails and a 14-stop road trip as siblings.
- No coordinates, so nothing can be plotted or deduped by location. Watkins Glen was already in the list as a one-line mention inside Finger Lakes and nearly got a duplicate.
- No source. The Instagram post a place came from is not recorded, so the overlay text and the video are lost once the save is gone.
- No link from a destination to the trip that eventually plans it (Zion is in the wishlist and in `usa-southwest-rockies/`, with no pointer either way).
- Two copies to keep in sync by hand.
- Capture cost is high: each add was a 25-line callout written by hand, with the risk of a wrong region (Mont du Dome's region came from a caption).

### 1.5 Process gaps

- No hooks in `travel/.claude/`. A page can be written with external JS, an empty `trip-date`, or a failing contrast gate and nothing stops it.
- No pre-publish gate. `publish.sh` deploys whatever is on disk.
- No tests for `_system/build.py`, `gallery.py` or the hub generator, although the house rule is tests for everything testable.
- Conditions re-check routines (skill Phase 2) are listed as "not yet scheduled" on four plans. Nothing enforces them.
- The skill is one 250-line file that mixes research lanes, writing rules, HTML rules, photo pipeline, QA and publishing. It is good content, but a single skill cannot be invoked for just one lane, and sub-agents get the whole thing or a hand-typed brief.

## 2. Target design

### 2.1 Repo layout

```
travel/
  CLAUDE.md                     repo rules, short; points at skills
  README.md                     how to add a destination, start a trip, publish
  trips.json                    trip index: slug, status, dates, region, theme (drives the hub)
  locations/                 the laundry list (section 2.2)
    locations.json           one file, all places, hierarchical ids
    collections.json            road trips and multi-stop ideas
    WISHLIST.md                 GENERATED tree view, grouped country > region > area
    inbox/                      raw captures (screenshots, export JSON) before resolution
  <trip-slug>/
    trip.json                   dates, bases, party, theme, classifier, status
    data/                       places, days, bookings, trails, adventures (JSON)
    PLAN.md                     generated tables + written prose
    index.html                  built
    research/                   research-*.md (move out of the root)
    gallery/                    gallery.json, spec, picks (candidates ignored)
    assets/                     files that SHOULD publish (kml, csv, gpx)
    archive/                    superseded plans and pages, never published
  _system/
    build.py  base.css  base.js  layout.html  themes/
    components/                 day card, stop card, booking row, timeline, emergency block
    tools/                      sun.py, photos.py, links.py, anchors.py, hub.py, publish checks
    tests/                      pytest for gates, hub, sun, gallery verify
  .claude/
    skills/                     section 2.4
    agents/                     research lane sub-agents, section 2.4
    settings.json               hooks, section 2.5
  publish.sh                    thin: calls _system/tools/publish.py
```

Moving `research-*.md` into `research/` and gallery files into `gallery/` is what lets `publish.sh` become an allow-list with no risk of shipping scratch.

### 2.2 Destination capture: the laundry list

Principle: capture is cheap and structured; research happens later, when a trip is started. The store is data, every view is generated, and there is one copy.

**Hierarchy.** Four levels, each a node with a stable id:

```
country            CA
  region           CA/AB                 province or state
    area           CA/AB/banff            park, valley, city, resort, lake district
      place        CA/AB/banff/lake-louise   trail, viewpoint, waterfall, activity, town
```

A place always has a parent area, an area always has a region, so "Lake Louise" is findable by typing any of its ancestors. A collection (road trip) is an ordered list of place ids with its own notes, so the Gaspesie post becomes one collection and 14 places, not one blob.

**Record shape** (one JSON object per place):

| Field | Example | Source |
|---|---|---|
| `id` | `CA/QC/charlevoix/mont-du-dome` | derived |
| `name`, `local_name` | Mont du Dome | you |
| `kind` | trail, viewpoint, waterfall, park, town, activity, lodge, drive, museum | resolver suggests, you confirm |
| `lat`, `lon` | 47.76, -70.52 | Wikidata or Nominatim |
| `parent` | `CA/QC/charlevoix` | Wikidata P131 chain, confirmed |
| `tags` | fall-colours, family, roadside-parking | capture |
| `season` | `["Sep","Oct"]` or null | capture, may be empty |
| `kid_fit` | yes / strong-kid / no / unknown | capture |
| `stats` | `{km: 9.5, gain_m: 543, hours: "3.5-4"}` | from the post, flagged unverified |
| `sources` | `[{type: instagram, url, saved: 2026-10-15, screenshot: inbox/..jpg, caption: "..."}]` | capture |
| `status` | idea, shortlisted, planned, visited, dropped | you |
| `trip` | `patagonia-feb-mar-2027` once a trip adopts it | set by trip-planner |
| `verified` | false until a research lane checks it | research |
| `notes` | free text | capture |
| `added` | 2026-10-15 | derived |

**Capture workflow** (`/destination add ...`, section 2.4):

1. Input: a name, a screenshot, a pasted caption, or an export file. Several at once is normal.
2. Extract place names. For a screenshot, read the text; for a video post, the caption first, then frames if the caption is bare.
3. Resolve each name: Wikidata search (free, structured, gives coordinates and the administrative parent chain), fall back to OpenStreetMap Nominatim (one request per second, user agent required). Return the top candidate with its parent chain and ask only when ambiguous ("Moss Glen Falls: Stowe or Granville?").
4. Dedupe by id, then by name within 2 km. Watkins Glen would have matched the Finger Lakes child.
5. Write the record, save the screenshot into `locations/inbox/`, regenerate `WISHLIST.md`, commit, push.
6. Reply with one line per place: name, resolved parent chain, kind, and anything it could not resolve.

**Views.** `WISHLIST.md` as a collapsible tree by country > region > area, each place one line with kind, season, status and a map link; a `/wishlist/` page on the live site with the same tree plus a single map of every pin; the Obsidian `Location.md` either retired or regenerated from the same data so there is exactly one source. Recommendation: retire it, keep a short Obsidian note that links to the published wishlist page.

**Instagram and Facebook intake.** The data export (Accounts Center, "Saved", JSON) gives links and captions in bulk; the browser pass gives captions and location tags for the posts whose caption is bare. Both feed step 1. On-screen text in a video needs `yt-dlp` plus frame extraction and reading, which is slow; run it only for posts where the caption names nothing. A pilot of 10 posts tells you the hit rate per source before committing to the rest.

**Migration.** The 26 entries in `Location.md` become the first `locations.json`. I would do it with the resolver so every entry gains coordinates and a parent, and keep the Why/Notes text as `notes`.

### 2.3 Trip data model and the page spine

**Data first.** Adopt the canadian-rockies pattern everywhere: `trip.json` plus `data/*.json` generate the PLAN.md tables and the page, and the prose (orientation, day narrative, decision rules) is written once in PLAN.md and pulled into the page. One shared builder in `_system`, no per-trip `build_page.py`; a trip supplies data and prose, not code. Per-trip scripts become `_system/tools/`:

| Tool | Replaces | Note |
|---|---|---|
| `sun.py <trip>` | 5 copies of sun-times, dark-times | Reads bases and dates from `trip.json`; writes `data/sun.json` and the light table. Also azimuth and elevation, which the skill asks for and the copies do not compute. |
| `photos.py` | photos.py, fetch_photos.py, verify_photos.py, shots.py, verify.py | Thin wrapper on `gallery.py` for hero and card images. |
| `links.py`, `anchors.py` | the Rockies checkers | Run by the verify skill and the pre-publish hook. |
| `hub.py` | the heredoc in publish.sh | Reads `trips.json`, not scraped HTML. |

**The page spine.** Fixed order so a reader learns it once, and so the pre-trip and on-trip phases are separated. Sections marked (new) do not exist yet as components.

| Phase | Section | Contents |
|---|---|---|
| Open | Hero | Image, title, dates, countdown, the trip in numbers strip |
| Open | The answer first | What changed from the brief and why, 5-10 lines |
| Before you go | Timeline (new) | One row per deadline, grouped T-90 / T-60 / T-30 / T-14 / T-7 / T-1 / day-of, generated from `data/bookings.json`. Each row: checkbox (persists), what, provider link, cost, refund terms, status. This replaces the bookings table as the primary view; the table stays in Reference. |
| Before you go | Documents and entry (new) | Passports with the validity rule computed from the return date, visas or eTAs, rules for minors crossing borders, insurance requirement, IDP, park passes bought online. One checklist. |
| Before you go | Packing (new) | Generated from a trip profile (hut, van, glacier, kids, altitude, rain) and edited by hand. Checklist. |
| Orient | What this place is, why it is famous, sub-region cards, what to know | Already defined by the skill |
| Orient | Photo gallery | Already defined |
| Orient | Bases and route | Night split table with the defence column; route order and rejected orders |
| Days | Day N (one section each) | Time chips, stop cards, Track A/B/C where it applies, embedded map, sun times, a **weather rule** chip (new: "If gusts > 50 km/h at 07:00, do Plan B"), a **Plan B** card, and the day's **day-of links** block (closures, forecast, parking, tel). The day-of links move from a page-level block into each day, because that is where they are tapped. |
| Reference | Trails, Adventures with limits, Where to stay, Budget (new standard), Hazards, Gotchas | Tables. Budget: per person and per group, currency, the date the prices were read, and a "2026 pattern" stamp when the year is wrong. |
| Reference | Emergency (new) | Per base: emergency number, nearest hospital with map link, mountain rescue, embassy, insurer 24 h line, the rental company's roadside number. |
| Close | State of knowledge, Open questions, Change log | Already defined on the newest plans; make it mandatory |

**Behaviour to add to `base.js`** (still no external JS): a "today" mode that, when the current date is inside the trip, opens the page on today's day and shows its sun times and weather link at the top; booking-row checkboxes persisting like the checklist; a "copy this day's addresses" button that produces a plain text list for a phone's maps app. All three are small.

**Hub page.** Generate from `trips.json`: filters by status (idea, researching, planned, booked, done), a map of every trip and every wishlist pin, and a link to the wishlist page. The custom domain is a one-time Cloudflare Pages setting once you choose it; nothing in the repo changes except the hub footer.

### 2.4 Skills and agents

Split the one skill into an orchestrator and single-purpose skills, each invocable on its own, and define the research lanes as sub-agent files so an orchestrator can launch them by name with a fixed output contract.

**Skills** (`travel/.claude/skills/`):

| Skill | Trigger | Does | Model |
|---|---|---|---|
| `destination` | "add X", a screenshot, "what do we have in Quebec" | Section 2.2: extract, resolve, dedupe, write, regenerate views, commit | Sonnet for capture; Haiku for bulk export parsing |
| `trip-planner` (orchestrator) | "plan X", "start the Peru trip" | Creates the folder from `trips.json`, adopts wishlist places, launches research agents, synthesises PLAN.md, calls build, verify, publish, schedules the conditions routine | Opus for synthesis (house rule), agents as below |
| `trip-build` | "rebuild the page" | `_system` build from data and PLAN.md; gates | Sonnet |
| `trip-photos` | "find photos" | Commons pipeline, one sequential searcher, contact sheet review | Haiku search, Sonnet review |
| `trip-verify` | before every publish | Build gates, self-containment, meta present, links, anchors, screenshot slices read, WCAG | Sonnet |
| `trip-publish` | "publish" | Allow-list copy, hub from `trips.json`, wrangler deploy, verify live URL returns 200 | Sonnet |
| `trip-conditions` | at plan time, and by the hook when a dated trip has none | Creates the one-shot cloud routine for T-2 days: forecast, closures, road conditions, foliage or snow, ending in one named verdict | uses the `schedule` skill |
| `trip-fares` | "what do flights cost", "watch the price" | The Google Flights and Booking.com method proven on 14 Oct (tfs URL edit, one-way tail bytes, NBSP regex); writes `research/fares-*.md`; optional weekly price-watch routine | Sonnet |

**Research sub-agents** (`travel/.claude/agents/`). Each writes exactly one `research/<lane>.md`, every claim with a URL, `GAP:` for the unverified, raw data not prose. The orchestrator launches them in one message.

| Agent | Lane | What it must return | Primary sources |
|---|---|---|---|
| `research-trails` | Trails and hikes | km and mi, gain, time, difficulty, trailhead coords, parking capacity and fill time, closures, what you see at the top, offline-map tier, kid suitability, alternatives | Official park pages, Waymarked Trails (OSM), AllTrails (link only, fetch 403s), Komoot, Outdooractive, Sepaq, Parks Canada, NPS |
| `research-adventure` | Activities with hard limits | Price in local currency, minimum age, height, weight, booking channel, operating window, weather cancellation and refund terms | Operator pages first; Civitatis, GetYourGuide, Viator as a cross-check |
| `research-sights` | Viewpoints and attractions | Hours, dates, prices, reservation needs, best light, crowd pattern by hour and weekday, which photo it is famous for | Official sites, Wikipedia, Commons geotags, Google Maps popular-times (manual) |
| `research-logistics` | Routes, borders, transport | Route options with time and tolls, border waits, fuel, cell dead zones, drive times between every stop pair, domestic flights and rail | Google Maps dir links, 511 road sites, border wait pages, rail operators, airline sites, Rome2Rio (link only) |
| `research-stays` | Bases | Elevation, car-free or not, how reached, tourist tax, when the valley loses sun, overnight temperature, supermarket, last transport, price snapshots for the party | Booking.com via the Playwright method, tourism-board directories, Numbeo |
| `research-timing` | Season, light, conditions | Peak dates by sub-region, live-condition sources, sun azimuth and elevation per date, climate normals, typical wind | Open-Meteo (free, no key, forecast and 80-year archive), national climate normals, sunrise computed locally, foliage and snow trackers |
| `research-entry` | Documents and safety | Passport validity rule, visa or eTA, rules for minors, insurance requirement, advisories, local emergency numbers, hospitals per base, embassy | travel.gc.ca destination pages, consulate pages, IATA Timatic (via airline sites) |
| `research-fares` | Costs | International, domestic, lodging and car by date window for the party, in CAD, with the read date | Google Flights, Booking.com, rental aggregators, frankfurter.app for FX |
| `research-community` | What the brochures omit | Recent trip reports, parking and crowd reality, closures people hit, scams | Reddit, TripAdvisor forums, blogs, YouTube transcripts via the existing `youtube-transcript` skill |

Rule of thumb for lanes on a city trip: `research-trails` becomes neighbourhoods and walks, `research-adventure` becomes tours with age limits; the output contract does not change.

### 2.5 Rules and hooks

Hooks live in `travel/.claude/settings.json` and run scripts under `_system/tools/`. They enforce what the skill currently only asks for.

| Hook | When | Checks | On failure |
|---|---|---|---|
| PostToolUse Write/Edit on `*/index.html` | every page write | self-contained (no external script, no local stylesheet), the four `trip-*` meta present, no hex outside themes, gallery markers present | non-zero exit, the message names the gate |
| PostToolUse Write/Edit on `locations/locations.json` | every capture | schema valid, ids unique, every place has a parent and coordinates, regenerate `WISHLIST.md` | non-zero exit |
| PreToolUse Bash matching `publish.sh` or `wrangler pages deploy` | before deploy | `trip-verify` passed on every changed trip in this session, `trips.json` and the folders agree, no non-allow-listed file would ship, every dated trip less than 60 days out has a conditions routine id recorded | block with the reason |
| PostToolUse Write on `*/PLAN.md` | plan written | the mandatory sections exist (answer first, orientation, bookings, hazards, state of knowledge, open questions, change log) | warning, not a block |

Rules to add to the repo CLAUDE.md, each one earned by a real incident:

- Weather and conditions: no dated trip within 60 days without a scheduled T-2 conditions routine (four plans currently say "not yet scheduled").
- Fares: every price carries the date it was read and the currency; "from" fares are never written as quotes (the Patagonia plan carried a per-person "from" fare as if it were the trip's price).
- Nonstop flights are a GAP until seen in a schedule tool for the actual dates (the plan assumed one that Google Flights does not show).
- One Commons searcher at a time, never parallel agents (the 2026-10-12 429).
- Deletions ask first and state what is lost (house rule).
- Push after every verified change (house rule); one branch per trip when a plan is being reworked.
- Numbers from a social post are `unverified` until a research lane confirms them; they are stored, not trusted.

### 2.6 Public sources worth standardising on

| Need | Source | Access notes |
|---|---|---|
| Place resolution, parent chain, coordinates | Wikidata API | Free, no key, structured. P625 coordinates, P131 administrative parent. |
| Geocoding fallback | OpenStreetMap Nominatim | Free; 1 request per second; user agent required; no bulk. |
| Trail geometry and length | Waymarked Trails, OSM Overpass | Free; official routes only where mapped. |
| Trail stats and reviews | AllTrails | Link only; fetches return 403. Report official figures beside it. |
| Park alerts, hours, fees | Parks Canada, NPS (alerts API with a free key), Sepaq, APN Argentina, national equivalents | Fetchable. Hours change; stamp the read date. |
| Weather forecast and climate archive | Open-Meteo | Free, no key, JSON, 16-day forecast, hourly archive back to 1940. Use for "typical wind in week 10". |
| Mountain weather | MeteoBlue, Windy | Link in day-of block; not fetchable for data. |
| Sun times, azimuth, elevation | Computed locally (`astral` or the existing formula) | No network needed. |
| Road conditions | Ontario 511, DriveBC, Alberta 511, Quebec 511, state DOTs | Links in day-of block; some have JSON feeds. |
| Avalanche, wildfire, air quality | Avalanche Canada, NASA FIRMS, AQHI | Links; FIRMS has an API. |
| Borders | CBSA and CBP wait-time pages | Links; CBP has an XML feed. |
| Flights | Google Flights via Playwright (proven method), airline schedule pages | Domestic Argentine schedules load about 100 days out. |
| Lodging snapshots | Booking.com via Playwright | Median of 12 family-suitable results with review 8+; cheapest-first returns hostel beds. |

| Travel advisories and entry | travel.gc.ca destination pages | Authoritative for Canadians; includes rules for minors. |

## 4. Other observations

- The Obsidian vault and the travel repo are separate repos, and the destination list currently lives in the one that has no build or publish path. Moving the list into `travel/` is what lets the wishlist page, the map and the trip link exist.
- `urban` is the only theme no trip uses. Keep it; a Buenos Aires or Hanoi city block would use it.
- The Vermont page has an in-page "Archive of earlier versions" section. Once `archive/` folders exist that section should go; a plan page should not carry its own history.
- `publish.sh` scrapes `<title>`, `.sub` and the hero image from each HTML file. Three trips have an empty `trip-date` and sort to 2099. `trips.json` removes the scraping and the special case.
- `canadian-rockies` is 409 KB because it inlines 15 days with three tracks each. That is fine for a page read offline, but it argues for the "today" mode so the reader is not scrolling 400 KB at a trailhead.
- The Patagonia fares file I wrote on 14 Oct is the prototype for `research-fares`; its method is recorded in memory so it is not re-derived.
