## 1. The rule (question 1)

### 1.1 Is `page - chrome_now + chrome_then` against the baseline page sound?

Yes. Write a baseline page as `content_then + K`, where K is its chrome then. The rule's ratio is
`(content_now + K) / (content_then + K)`: the whole-page ratio the page would have if the shell had never changed since
the baseline. This keeps the meaning of 1.25, P8 still counts every content byte, and shell growth since the baseline
leaves the ratio. That growth is 72 B on the public build and 1737 B on the sign-in-on build, and Q222 and Q260 asked
for exactly this.

The brief's literal step 3 (`page - chrome` against `baseline - chrome`) divides content by content. With the shell
the part that did not grow, it raises every ratio: 1.2622 at the median, so main fails by 870 B. Because the 1.25, 1.5
and 2.0 limits are fixed, that reading would tighten the budget. The brief forbids that ("Must not touch ... the 1.25,
1.5 and 2.0 caps"), and so does its own Room-today line, which expects BUD-1 to give room. The builder's reading is the
only one consistent with the whole brief, and the commit message records that the other one was measured and
rejected. A deviation from a brief is still a deviation, so MASTER-ORDER 6.1 step 3 and the BACKLOG row must be
updated to say what was built (M4).

**Owner ruling on the formula: not needed.** Q260 decided what (catalogue content only, with the shell under its own
cap), not the arithmetic, and this formula is the one that leaves the owner's 1.25 unchanged. Record it as an FYI on
the Q260 row: "S13 holds the shell at its baseline size."

### 1.2 Can a shell edit never move S13?

Almost never. "Never" is too strong, and the module header (`budget-report.mjs` lines 9 and 10) says "cannot move
S13". Shell bytes that the measure leaves in content are:

| Leak | Size (measured or derived) | Direction |
|---|---|---|
| A new client chunk that a shell component pulls in: one `<script src="/_next/static/chunks/x.js" async="">` per page | 70 B (80 B for a turbopack runtime chunk), measured on the four pages | charged to content |
| A chunk ref added to the module rows (`,\"$5\"`) | 7 B per row | charged to content |
| Row-id renumbering: a new shell row shifts later ids, and every content ref that crosses `f`/`10` or `ff`/`100` grows a byte | a few to about 13 B | charged to content |
| The `null` slot left in the layout's children when the beacon is off | 4 B (beacon and no-beacon fixture S13 differ by exactly 4 B) | charged to content |

All of these are charged to content, the safe direction: no content byte hides in the shell. But the median has 113 B of
headroom, so one shell change that adds a client chunk (70 + 7 B, plus renumbering) can fail S13 on its own. That is the
failure BUD-1 exists to stop. The planned consumers make it likely: GSI-P is a link, but NAV-1 and FBK-2 touch client
shell components. The "13 to 70 B" the builder mentions is this list. Fix: S2.

### 1.3 Can content growth hide inside the chrome?

Only up to the chrome cap, which is checked on the largest page of the build. The paths are:

- **Content rendered inside the shell.** A per-place breadcrumb in the header, or a per-page `ReportLink` prop in the
  footer, would count as chrome. The cap bounds it, and the test "same shell on a place, a trip and the home page"
  (`place.total === trip.total`) catches a page-specific shell prop the first time it appears. Good.
- **A row shared by chrome and content.** It is handled: the `elsewhere` scan keeps a row in content when anything
  outside the chrome refers to it (`next/link`'s row, `$Lc` in the footer of `bolzano`, stays content). There is a gap:
  the `REF` and `elsewhere` regexes only see `"$<id>"`, `"$L<id>"` and `"$@<id>"`. They miss `"$Q<id>"`, `"$W<id>"`
  and React 19 path refs `"$27:props:model:..."`. A trip page carries 8 path refs, and place pages carry 3 `$Q` refs
  each. A row that the chrome refers to by `$L`, and content refers to only through one of those forms, would be
  claimed as chrome. Today no chrome row is in that position (checked on all four pages). Fix: S3.
- **Rows that follow a text row.** A `T` row has no newline at its end, so the next row does not start a line, and
  `rowsOf` cannot see it. That is 1 to 4 rows per page (`lake-louise`: rows 25, 27, 32 and 34). A chrome-only row in that
  position would be missed. That undercounts the chrome, the safe direction. Fix: S3.

### 1.4 Can a larger future shell pass silently because the baseline chrome is fixed?

S13 no longer sees the shell at all, by design. The chrome cap is the only gate, and it is a fixed number of bytes. It
does not drift with the baseline, so it is the right shape. Three things weaken it:

- **Its inputs are not pinned (M2).** `CHROME_TODAY_BYTES`, `BEACON_ALLOWANCE_BYTES` and `OVER_50` now live in
  `web/scripts/`, and no test pins their values. The test checks `CAP == TODAY + ALLOWANCE + 1024`, so raising
  `CHROME_TODAY_BYTES.public` from 4004 to 5004 passes every test. The 1.25, 1.5 and 2.0 limits are pinned; these
  numbers set the slack and need the same treatment.
- **The baseline `chrome` column is not checked (M2).** Lowering a page's `chrome` value loosens S13 for that page
  one for one: setting all 209 to 0 gives about 4 KB of headroom on every page. The test checks only that the keys match.
- **The sign-in-on build is never gated (S1).** check-all and the vitest setup build only the public app and two
  public fixtures. `CHROME_CAP_BYTES.signIn` (7043 B) and the sign-in-on S13 median (1.2487, 100 B headroom) are only
  checked when someone builds with the flag by hand. The old rule was failing that build by 1637 B and nobody saw it,
  which shows this matters.

### 1.5 Is 1 KB of headroom reasonable? Is the 350 B beacon allowance right?

- **1 KB is right.** It is the number in Q260. GSI-P (one footer link, about 150 to 200 B as markup plus payload) and
  FBK-2 fit, and NAV-1 is planned to free about 1 KB.
- **350 B is an exact figure for the tag.** The tag is 320 B in the fixture with a 17-character token: 151 B markup
  and 169 B payload. It grows 15 B per copy for a 32-character Cloudflare token, and there are two copies, so
  320 + 2 x 15 = 350. The fixture test proves both copies. The allowance has zero slack, which is acceptable because the
  number is derived, not guessed. Charging it to builds without the beacon (`chargedChrome`) is the right idea: the cap
  then holds the deployed page.
- **But the cap is today + 350 + 1024, and that is not what was approved (M1).** Q260 says "today's bytes + 1 KB".
  MASTER-ORDER 4.5 lists the beacon as a consumer of that 1 KB ("Shell chrome ... today + 1 KB | GSI-P, NAV-1, FBK-2
  (`ReportLink`), beacon"). The builder added the allowance on top, so the shell may now grow 1374 B, not 1024 B. That
  loosens an owner-approved number. Either keep the allowance inside the 1 KB (cap 5028 B public, 6693 B sign-in on;
  674 B headroom once the beacon ships, still enough for GSI-P and FBK-2 with NAV-1 freeing about 1 KB), or ask the
  owner. My recommendation: keep it inside the 1 KB, as planned.

## 2. Correctness of the chrome measure (question 2)

- **Markup.** Each part is found by its opening tag (`<header class="site-header"`, `<footer class="site-footer"`,
  `<nav class="bottom-bar"`, the beacon `<script src>`), and its end by same-name nesting depth. That is correct for this
  shell: the header's inner `<nav>` is not counted against the bar, because each part matches only its own tag name.
  A class list such as `class="site-footer x"` stops the match, and the error is then loud ("expected one footer element"),
  which is the intent.
- **Payload.** The header and bar are found as `["$","$L<id>",...]` of the module rows named `SiteHeader` and
  `BottomBar`; the footer as the `footer` element whose first prop is `className: "site-footer"`; the beacon as the
  `script` element with its `src`. Then come the rows referred to only from inside those ranges, followed transitively,
  and the ranges are merged so no byte counts twice. Measured on `lake-louise`: rows 8, d, e and f (SiteHeader,
  ReportLink, UnitSwitch, BottomBar: 50 + 149 B), header 23 B, footer 554 B, bar 49 B, a total of 825 B. All are
  plausible and none is content.
- **Exactness.** `encodedBytes` re-escapes each decoded slice the way Next writes it (`JSON.stringify`, then `& < >
  U+2028 U+2029` as `\uXXXX`) and subtracts the 2 quotes. Ranges start and end on ASCII `[`, `]` or a newline, so a
  slice never splits a character. Every page has one push, but the code handles several. The claim "exact" holds for
  the payload share. It does not hold for the push wrapper (43 B per push) or the leaks in 1.2; the commit claims
  neither, but the module header's "cannot move S13" overreaches.
- **Loud failure.** The code throws when a part is missing from the markup or the payload, appears twice, or when the
  beacon count differs between them. The unit tests cover a missing bar in the markup and a missing footer in the
  payload. They do not cover a missing header, a duplicated part, or a beacon mismatch (S5).
- **Redirect and error documents.** The real build has 3 of them under `places/`
  (`waterton-red-rock-parkway`, `canmore-nordic-centre-provincial-park`, `lake-louise-sightseeing`), none in the
  baseline. They measure as `shell: false`, and the cap test skips them, which is right. But `placeRows` does not check
  `shell`. If a baseline place became a redirect (a slug rename), it would count as a 3 KB page at a ratio of about
  0.05, pulling the median down without a word (M3). The old rule had the same hole; BUD-1 is the place to close it.
- **Script tags of 13 to 70 B.** These are chunk tags, chunk refs and renumbering (1.2). They are left out of the
  chrome, which is defensible because chunks are shared. They need to be documented and made visible to a shell lane
  (S2), not silently absorbed.

## 3. The 26 B offset (question 3)

**Cause (derived from the code; confirm with one build):** the 56 re-baselined page sizes in `1726dfeb` were measured
on the D2b-INT integration build. That build's tip, `d6faa6eb`, merges main only up to `52339a05` (ANSWERS-2). It
predates ACCT-PH (`7ab0657e`), which reached main in the same window, before `41ca7f47` and `1726dfeb`. In the public
build, ACCT-PH's only HTML change is the new prop on the bar:
`<BottomBar account={capabilities.signIn ? <AccountItems /> : undefined} />` serializes as
`["$","$Le",null,{"account":"$undefined"}]` where it used to be `["$","$Le",null,{}]`. That adds 22 characters with 4
escaped quotes: 26 B, every page, all inside the bar's payload subtree. The CSS change is in the stylesheet, not the
HTML. So the builder's rebuild of `1726dfeb` (with ACCT-PH) is 26 B larger than the recorded sizes on all 56 pages,
with the difference entirely in chrome.

**Consequence:** the `chrome` value stored for those 56 pages (4004) is the chrome of a different build than the one
their `pages` bytes come from. It should be 3978. Today each of them is charged 26 B too much in S13 (stricter by about
0.0003 of a ratio). The median page (`cinque-torri`) is in the 3932 group, so the current median is unaffected. The
error points in the safe direction and is small, but the note in `place-html-baseline.json` says the 1726dfeb rebuild
"gives the 56 D2b-INT pages", which suggests it reproduces them. It does not.

**To confirm, one measurement:** build `d6faa6eb` (the D2b-INT tip) in a scratch worktree with the same environment.
Check that the 56 pages reproduce their recorded bytes exactly, and that `chromeOf` gives 3978. Then set the 56 values
to the measured number and say so in the note (S4). If the owner rules Q88 against option A, revert those 56 rows of
both `pages` and `chrome` together.

## 4. Test quality (question 4)

- **Limits pinned:** `[1.25, 1.5, 2]` (`place-size.test.ts`), `START_JS_BUDGET_KB === LIST_BUDGET_KB` (200), and
  `CHROME_HEADROOM_BYTES === 1024`. All stay as required. Not pinned: `CHROME_TODAY_BYTES`, `BEACON_ALLOWANCE_BYTES`,
  `OVER_50` (42 slugs; it used to sit in the test file, so adding a slug was a test edit, and now it is not), and the
  baseline `chrome` values (M2).
- **Does `shell-size.test` fail when it should?** Yes, for the cases that matter. Chrome over the cap fails the cap
  test. A renamed or missing shell part throws inside `chromeOf`, which fails the whole file. A build with no pages
  fails the `> 70` guard. The fixture-pair test fails if the beacon outgrows its allowance at a production token
  length. The synthetic `page()` tests check the arithmetic exactly (footer +70 is +70 in markup and +70 in payload;
  main content moves nothing; the exact payload sum).
- **Gaps:** no synthetic case of a row shared by chrome and content (the key honesty property in 1.3); no case for a
  missing header, a duplicated part, or a beacon mismatch; no case for a row after a `T` row (S5).
- **`place-size.test` can still skip everything.** All three S13 checks are `it.skipIf(sizes.length === 0)`. If the
  place path in the export view changes, S13 turns silently green (M3). The old file had this hole too.
- **T1 acceptance does not match the method.** The brief says 70 bytes added to `SiteFooter.tsx` "moves the chrome
  measure by 70 ± 10". The measure counts footer text in markup and payload, so it moves by about 140, which the
  builder's own unit test asserts. The brief is wrong, not the code, but the hand-back must say so. The commit records
  no scratch-build evidence for T1's two real-build checks (footer +70, place section +70) (S6).
