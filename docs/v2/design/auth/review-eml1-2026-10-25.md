# EML-R design review: the passwordless-first sign-in card and `/sign-in/reset/`

Reviewer: travel-design-reviewer (Opus 5.5), 25 Oct 2026. Branch `public/EML-1` at `57fdb0f` (card `3aad441`, e2e and
shots `59981ce`), worktree `travel-wt/v2-EML1`. Not merged, not pushed.

Evidence:
- All 84 builder shots (21 states x 1440 and 390 x light and dark, 2x) read one by one.
- Own probe on the fixture build `web/.fixture-auth`: `next start` on port 4817, Chromium with the Metal GPU flags,
  network mocked as in `tests/e2e/auth-mock.ts`, dark mode set with the header's own "Switch to dark theme" button.
  The probe covered:
  - a keyboard-only walk;
  - a paste of "482 913" into the code field;
  - a fake clock for the 60 s cooldown and its live region;
  - a resend;
  - every step at 320 px with an 85-character address;
  - the reset page under 429 and SEND_FAILED;
  - the requests that `/`, `/trips/`, `/places/` and `/about/` make.
- Probe shots are in the scratchpad (`eml1-shots/review/`). The server was stopped by PID. No Playwright e2e was run.

Spec: `docs/v2/features/email-sign-in-and-account-emails.md`, read in this order: Decision 25 Oct, 3, 4, 5, 13 (EML-1),
the EML-0 results and the build notes. Also the Google spec, G-rows and F12 (the button).

## Verdict: ship after fixes

The card is right in shape and in tone:
- One field first, then a plain chooser.
- The address stays visible in a quiet `--well` strip with "Change", in every step.
- The Phase 1 sender note is word for word, and the code lifetime says 5 minutes everywhere.
- Known and unknown addresses read the same, and nothing a visitor typed is echoed back.
- There is no green and no purple, and every colour comes from a token.
- Nothing leaks to public pages.

Five things fail P4 ("no dead ends") or WCAG 4.1.3 and must be fixed before merge:
- The reset page tells a person who forgot their password to "use your password".
- A wrong code is never announced to a screen reader.
- A resend gives no sign that it worked.
- A dead code leaves its form live.
- The cooldown question needs an answer built in.

None of this needs rework. Each fix is in one or two files.

## What I checked and found right

- **The chooser copy, "How do you want to sign in?"** (and "...sign up?"). It is a plain question with two verb
  buttons, so keep it. The help line under the buttons needs a change: see S3.
- **The serif step headings** (`--t-title`, 17 px serif, 600).
  - They give each step a name without competing with the condensed uppercase `h1`.
  - At 390 the pairing reads as page, then step.
  - At 1440 the card is left-aligned under the `h1`, which matches the account page.
- **The `--well` address strip.**
  - Light: `--ink` on `--well` is 13.92:1. Dark: 15.94:1.
  - "Change" in `--accent-text` on `--well` is 5.49:1 light and 9.21:1 dark.
  - The strip has no border, so it does not read as an input. In dark mode it sits darker than the card, like a recess,
    which is correct.
  - An 85-character address masks to `a…@mail.subdomain.example-company.co.uk`. It wraps inside the strip at 320 px, and
    "Change" drops to its own line with no overflow (probe `w320-chooser-429.png`).
- **Text actions** (underlined mono in `--accent-text`).
  - They are clearly secondary to the amber button, and their style is consistent across all three steps.
  - Stacked on a phone, each is a 44 px box (probe: "Forgot password?" 141x44 at y 466, "Email me a code instead"
    195x44 at y 514, so 48 px from top to top). That passes the 44 px rhythm, with 4 px between targets.
  - On desktop they sit side by side.
  - Inline links inside sentences ("Sign in", "Back to sign in") stay serif. That split (inline serif, standalone mono)
    is right.
- **The Show button.**
  - It is an outlined secondary `.btn` in mono, 61 x 46 px at 390 and 42 px tall at 1440, the same height as the field.
  - `aria-pressed` is set and the accessible name is "Show password".
  - It does not shrink the field below a usable width at 320 px. Keep it.
- **The reset page `h1`.** "RESET YOUR PASSWORD" fits on one line at 390 and at 320: the probe measured an `h1` height of
  32 px, one line, at both widths. No change needed.
- **The code field.**
  - It has `inputmode="numeric"`, `autocomplete="one-time-code"`, `pattern="[0-9]*"` and `maxlength=6`.
  - Text is mono at 20 px with 0.3 em tracking, and the field is 46 px tall at 390.
  - A paste of "482 913" becomes `482913` and submits by itself (probe).
  - Too many tries and an expired code both clear the field. Focus stays in the field after an error.
- **The cooldown.**
  - "Send a new code (in 1:00)" counts down once a second and is disabled.
  - The polite live region is empty while the count runs and says "You can send a new code now." at 0:00. It does not
    speak every second (probe at t=0, 20 and 61 s).
- **Heading focus between steps works on Chromium.**
  - After Continue, focus is on `h2 "How do you want to sign in?"`. After "Email me a code", it is on `h2 "Check your
    email"`, with a visible `:focus-visible` ring after keyboard use and none after a mouse click.
  - The Tab order after that: Change email address, Code, Sign in, Use my password instead, footer.
  - The disabled resend is skipped, which is acceptable because the live region covers it.
  - The WebKit Tab walk was skipped (accepted).
- **Honesty and privacy of the copy.**
  - No message echoes an address or a code.
  - The send answer is the same for known and unknown addresses (the guard fixes the body).
  - Sign-up for an existing address looks like success.
  - The sender note matches "Decision 25 Oct" exactly and appears on both the code step and the reset code step.
  - "The code works once, for 5 minutes." matches EML-0 U9.
  - No string says Google.
- **Budgets.**
  - `/`, `/trips/`, `/places/` and `/about/` load no auth stylesheet (no `.auth-card` rule in any sheet) and make no
    request to `challenges.cloudflare.com`.
  - Turnstile loads only on the first focus of the email field.
  - I did not re-measure the gzip sizes of the two chunks; the builder's 6.6 KB and 7.2 KB stand unverified by me.
- **Dark mode through the site's control.** The header button "Switch to dark theme" sets `data-theme="dark"`, and every
  state reads correctly in dark at both widths.

## MUST fix before merge

**M1. The reset page tells someone who forgot their password to "use your password".**
- Where: `web/lib/auth/auth-errors.ts` 32 (`sendFailed`) and 62 (`tooMany`, case `send`), called from
  `web/components/auth/ResetFlow.tsx` 51 with action `send`.
- What the probe shows on `/sign-in/reset/`:
  - under 429: "You've asked for several codes. Wait 15 minutes, or use your password.";
  - under SEND_FAILED: "We couldn't send the email. Try again shortly, or use your password."
- On `/sign-up/` the chooser shows the same 429 copy. "Create a password" takes from the same per-address send bucket
  (EML-Q build note), so the way out it offers fails too.
- Fix: add the action `reset-send` (and pass the page mode for sign-up). The copy:

| Where | Quota | Send failed |
|---|---|---|
| Reset page | "You've asked for several codes. Wait 15 minutes, then try again." | "We couldn't send the email. Try again shortly." |
| Sign-up page | Quota copy with no alternative | "We couldn't send the email. Try again shortly." |
| Sign-in page | Unchanged | Unchanged |

- Add unit cases to `web/tests/auth/auth-errors.test.ts` for each page.

**M2. Field errors after a submit are silent for screen readers; notice banners may be too.**
- Field errors:
  - `web/components/ui/Input.tsx` 30 renders `.field-error` with no role. The probe after a wrong paste found
    `role=null`, no live ancestor, and focus still in the code field.
  - A screen-reader user who pastes a code hears nothing when it fails. The same goes for expired, too many tries and
    "Use at least 8 characters".
- Banners:
  - `web/components/ui/Banner.tsx` 26 gives `notice` and `offline` banners `role="status"`, but the banner is inserted
    with its text already in it.
  - NVDA and VoiceOver often skip a status region that arrives with content. "We couldn't send the email" and
    "You're offline" may never be read.
- Fix: one persistent, initially empty `<p className="sr-only" aria-live="polite">` per card (in `SignInCard.tsx` and
  `ResetFlow.tsx`), mounted with the card. On every new `problem`, and on M4 and M5 statuses, write the message into it.
  Clear it first, then write it on the next tick, so a repeated message is read again.
- Keep `role="alert"` on urgent banners as it is.
- Do not add `role="alert"` to `.field-error` globally: it would fire on every form in the site.

**M3. Builder question: should "Email me a code" stay enabled during a 429? Decided: disable it, with the time left.**
- Where:
  - `web/components/auth/ChooserStep.tsx` 23 does not disable it;
  - `SignInCard.tsx` 63 already stores `resendAt` on a 429, but the chooser never reads it;
  - `PasswordStep.tsx` 54 ("Email me a code instead") and the reset `EmailStep` submit (`ResetFlow.tsx` 115-121) have the
    same gap.
- Why: today the button stays live under "Please wait a minute" or "Wait 15 minutes". Pressing it spends a Turnstile token
  and a guard call, and shows the same banner with no visible change, so the card looks broken (P4: visible current
  state).
- The code step already uses the opposite pattern ("Send a new code (in 0:42)", disabled). One rule for both is easier to
  learn.
- The fix:
  1. While a Retry-After from this card is running, disable "Email me a code" (and "Email me a code instead" and the reset
     submit) and put the time in its label:
     - "Email me a code (in 0:42)" while 10 minutes or less remain;
     - "Email me a code (in 15 min)" above that, updated each minute.
  2. Make "Use my password" the primary button for that time on the sign-in chooser, so the one live action is the amber
     one (P7). Keep "Use my password" enabled.
  3. When the time is up, re-enable the button, clear the banner, and say "You can ask for a code now." through the M2
     live region.
  4. Tie the wait to the address. Editing the address on the email step or the reset page clears it, because the guard's
     per-address bucket is keyed on the address. The IP bucket will answer again if it is the IP.
  5. Use the same treatment for a 429 on "Create account" (sign-up). The banner stays as the explanation, and the label
     carries the count.

**M4. A dead code leaves a live form.**
- Where: `CodeStep.tsx` 49, 100-126 and 128-130.
- After TOO_MANY_ATTEMPTS or OTP_EXPIRED:
  - the field is cleared, but the field and "Sign in" stay enabled;
  - the error says "Send a new code" while that action can still be disabled for up to 60 s (three quick wrong pastes
    happen well inside a minute);
  - typing again sends a dead code and gets "That code didn't work".
- Fix: when `problem.clearCode` is set:
  - mark the code dead: disable the code input and the submit;
  - show "Send a new code" as a full-width primary button in place of "Sign in" (with "(in 0:24)" while the cooldown
    runs);
  - while it waits, the error reads "Too many tries. You can send a new code in 0:24.";
  - a successful resend restores the normal form.

**M5. A resend gives no sign that it worked.**
- Where: `SignInCard.tsx` 82-93 and 103, `ResetFlow.tsx` 45-57, `CodeStep.tsx` 128-135.
- The probe after pressing "Send a new code": the label goes back to "(in 1:00)", there is no banner, and the live region
  is empty.
- A person who is unsure presses again a minute later. With 4 sends an hour per address, that is a 15-minute lockout after
  a few doubts.
- Fix:
  - on a successful resend, clear the code field;
  - show a `notice` line above the field: "We sent a new code to n…@gmail.com. Use the newest email.";
  - write the same text to the M2 live region.
- The words "Use the newest email" matter. Every earlier code is still in the inbox, and whether Neon still accepts an
  older code after a resend is not confirmed (add it to EML-E).

## SHOULD fix (this lane, or a named follow-up)

**S1. Put focus in the code field on the code step, not on the heading.**
- Where: `CodeStep.tsx` 95, through `StepHeading` in `parts.tsx` 10-19.
- With focus on the heading, a desktop user who copies the code from mail, comes back and presses Cmd+V pastes nothing,
  because two Tabs are needed to reach the field (probe walk). macOS Safari also offers the mail code only when the field
  has focus.
- Fix: on the code step, focus the input, and give it `aria-describedby` that also points at the lead line and the masked
  address, so a screen reader hears "Code, We sent a 6-digit code to n…@gmail.com, The code works once, for 5 minutes".
- Keep heading focus for the chooser and the password steps.
- Amend spec 3.4, which says "the step heading receives focus", to make an exception for the code step. Section 3.1
  already says "focus moves to the new field".

**S2. The unverified lead line leaves "to" alone on the second line at 390.**
- Where: `SignInCard.tsx` 143 (`13-unverified-confirm-*-390`).
- Fix: render "Confirm your email first." as its own sentence above the default lead, "We sent a 6-digit code to".

**S3. The chooser help line describes only the code option and sits under both buttons.**
- Where: `ChooserStep.tsx` 38.
- On `/sign-up/` it reads "No password needed." right under "Create a password". When the password button is first, it
  explains the second button.
- Fix:
  - tie it to the code button with `aria-describedby`;
  - word it "No password needed: we email you a 6-digit code.";
  - place it directly under "Email me a code" when that button is first, and drop it when the password button is first.

**S4. The sign-up password step has no way back to the code option.**
- Where: `SignInCard.tsx` 195 passes `onCodeInstead` only when `!signUp`.
- A code sign-in creates the account, so "Email me a code instead" is as right on `/sign-up/` as on `/sign-in/` (P3: the
  way back is visible).

**S5. Turnstile: say what is happening when it challenges.**
- Where: `TurnstileLazy.tsx` 67-75 and the slot at `SignInCard.tsx` 218 and `ResetFlow.tsx` 143.
- In interaction-only mode the widget appears in the slot at the bottom of the card. The button above it keeps spinning
  for up to 15 s, then the card shows "We couldn't confirm this browser".
- Fix:
  - pass `'before-interactive-callback'`: show a one-line `notice` above the slot ("Tick the box below to continue.") and
    `scrollIntoView({ block: 'nearest' })` the slot;
  - on `'after-interactive-callback'`, remove the line;
  - while the widget waits for a person, do not count the 15 s.

**S6. Coming back to the same address within a minute should go straight to the code step.**
- Change, the same address again, then "Email me a code" within 60 s today gives "Please wait a minute, then try again"
  (`10-rate-limit-minute`). The code from a moment ago is still valid.
- Fix: keep `resendAt` per address in the card. If the address matches and the cooldown is running, return to the code
  step without a call. M3 then covers the case of a different address.

**S7. Select the code on a wrong code.**
- Where: `CodeStep.tsx` 70-78.
- After "That code didn't work", typed digits are refused because `maxlength` is reached. Only a paste replaces the code.
- Fix: select the field's contents when an `INVALID_OTP` arrives, so typing replaces it.

**S8. Reset "Your password is set" drops `next`.**
- Where: `ResetFlow.tsx` 103 links to `/sign-in/`.
- Fix: carry the checked `next` (`/sign-in/?next=${encodeURIComponent(returnPathFromSearch(location.search))}` when it is
  not the default), so a family who reset mid-trip-page returns there.

**S9. Record two foundation deviations.**
- The disabled text action uses `--muted` with no underline instead of the foundation's 45% opacity. The text stays at
  6.94:1, which is better.
- The Google button (Google spec F12) will need Google's own hex values. They are the one exception to "colour only from
  `themes.css`", like the provider marks.
- I will add both to `docs/v2/design/foundation/components.md` when this merges. The builder needs no change for this.

## The Google slot (GSI-1)

The slot is clean, with three small changes to make when GSI-1 lands:
1. In `SignInCard.tsx`, render a `providers` node above `EmailStep` on the email step only (spec 3.1 and Google spec
   "Continue with Google first, full width; a divider 'or'"). Nothing else in the card moves. The 46 px button height
   matches the 46 px inputs at 390.
2. `memory.ts` 9: `Method` must gain `'google'` (spec 3.1 lists it), so a returning Google user sees the button first.
3. `auth-errors.ts`: restore "or use Google" to the quota and send-failed copy on the sign-in page only (the build notes
   left it out on purpose).

The step-1 card has no `h2`, so the page `h1` heads the Google button and the field. That is correct.

## Decisions the builder asked about

1. **Flags in `web/lib/auth/flags.ts`, not `capabilities.ts`: accepted.**
   - It reads the same `NEXT_PUBLIC_SIGN_IN` variable as `capabilities.signIn`, so the two cannot drift.
   - The design consequence: no client component outside the sign-in pages can know whether codes are on. A future
     "Sign in to save" prompt elsewhere must say "Sign in" only, never "we'll email you a code". Keep `flags.ts` imported
     only from server pages.
2. **Success goes straight to the checked `next`: accepted.** It saves a hop and a flash of the account page. S8 extends
   the same path to the reset "done" state.
3. **WebKit keyboard walk skipped: accepted.** Chromium evidence is above. Safari's "Tab highlights each item" setting is
   on the manual list below.
