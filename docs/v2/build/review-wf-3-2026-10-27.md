## Verdict

**Merge, at `7400faa5`, not at `e00a1efd`.** The workflow keeps every WF-2 property: no secret, `contents: read` on both new
jobs, untrusted values only through `env:`, credentials not persisted, and the scrub runs before each upload (every artifact scanned
clean). The new pins are real: `actions/cache` `55cc8345` is the `v6.1.0` tag commit (released 26 Jun 2026), and the
`postgres:18-trixie` digest `edb0c08d...` is the multi-arch index digest Docker Hub serves for the tag today (anonymous token,
manifest HEAD, 27 Oct). The cache design is correct: restore everywhere, save only on `main`. GitHub's own cache scoping means a
branch or fork run cannot write a cache that `main` restores, whatever the lint says. The db job is the right design: it builds
`tools/db` on the pinned base, publishes on loopback, uses `ci-` passwords, and waits on TCP until `travel_template` exists. Run
40437595674 on `7400faa5` is green end to end. S1 to S3 must land before WF-10 makes `check / summary` a required check, because each
of them lets "green" cover a check that did not run.
