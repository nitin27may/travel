# Build plan: the public read-only site (18 Oct 2026)

Step 1 of the owner's order of work ([product-direction-2026-10-18.md](../../design/product-direction-2026-10-18.md)):
the public site with no login, on the Trailhead foundation ([design/foundation/](../../design/foundation/)),
keeping everything in [keep-from-live-site.md](../../design/keep-from-live-site.md), with the map stack from
[research/map-stack-2026-10-18.md](../../research/map-stack-2026-10-18.md). It is sized for Sonnet coding
agents (`travel-builder`) working in parallel lanes with disjoint files.

This page decides where it is built, how the data is served, the lanes and their order, and the gates.
Each lane has its own brief in this folder.

## 1. Where it is built: `web/`

**Decision: build the public site in `web/` (the Next.js 16 static export), not in `prototype/` and not in a
new app.** The prototype stays the design bench for the signed-in planner.

| Option | For | Against |
|---|---|---|
| **`web/` (chosen)** | It *is* the live Trips and Places pages the owner wants kept: filter pills, group and sort, four views, saved views, columns, density, CSV, URL state, honesty markers, all with tests (url-state and places-parity e2e, privacy, visibility, no-hex, axe). It already self-hosts the three OFL fonts, reads `locations.json` and the legacy trip list, and fails closed on private trips. A read-only site needs no backend, so "working prototype end to end" and "production" are the same build: static pages, client-side filtering. Real URLs (`/trips/<slug>`) instead of hash routes, which the URL table requires. | Its colours are the old green shell, generated by `tools/theme_tokens.py`; every component needs re-skinning to the foundation (L0). Static export needs pre-rendered paths for the globe drill-down (handled in LD and L2). The prototype's public screens and trail panels must be re-built here, not copied. |
| `prototype/` (Vite, React 19, in memory) | Fastest start; already has the Dolomites trip, 18 researched trails, the place page and MapLibre. | Hash router; none of the live Trips/Places features exist there, so "keep the good stuff" means re-implementing what `web/` already does and tests. No visibility rule, no privacy test. Not in the pnpm workspace. Building twice: once here, again for production. |
| New app | Clean slate. | Throws away both. Nothing it gains is worth a third codebase. |

**How the prototype is reconciled.**
- `prototype/` keeps the planner (Plan, Today, Bookings, Tasks, Budget, Share) and its migration in
  [redesign/recommendation.md](../../design/redesign/recommendation.md) section 6, **steps 1 to 10**.
  **Steps 11 and 12 (public pages, Places and Globe in the prototype) are superseded by this plan.**
- The prototype's public screens (`Discover.tsx`, `PublicTrip.tsx`, `PlacePage.tsx`, `TrailPanels.tsx`,
  `Explore.tsx`) are frozen as reference and are not developed further.
- Its data (`prototype/src/data/trip.ts`, `places.ts`, `trails.ts`, `public-trips.ts`) stays the source
  for now. LD snapshots it into `web/` at build time, so neither app edits the other's files.
- When the planner is built for real (step 3 of the direction), it moves into `web/` under `/home` and `/t/`
  (patterns 1.2), reusing the L0 components. At that point the data moves into the store in `data/` and
  both read it from there.

### 2.2 The adapter API (LD owns; every other lane only imports it)

```ts
// web/lib/public/index.ts
listTrips(): PublicTripCard[]                 // listed (public) trips only
getTrip(slug: string): PublicTrip | null      // built trips (public + unlisted); private -> null
tripSlugs(): string[]                         // for generateStaticParams
listPlaces(): PublicPlaceCard[]               // locations.json + prototype places + trails, de-duplicated
getPlace(slug: string): PublicPlace | null
placeSlugs(): string[]
globeIndex(): GlobeIndex                      // pins by continent, country, state, district; counts; trips at first base
globePaths(): string[][]                      // every /globe/<cc>/<state>/<district> with content
legacyPlaceRedirects(): { from: string; to: string }[]   // old /places/<cc>/<region>/<area>/<place>/ -> /places/<slug>
```

Key types (full definitions in [LD-data-adapter.md](LD-data-adapter.md)):
`PublicTrip { slug, title, depth: 'full' | 'summary' | 'overview', dates, nights, bases[], days: PublicDay[],
categories: Record<Category, CategoryItem[]>, season, cover: Photo, gallery: Photo[], legacyUrl, honesty[] }`;
`PublicDay { n, date?, title, base, driveMin, driveIsEstimate, items: DayItem[], tracks?: Track[] }`;
`PublicPlace { slug, name, kind, subkind, category, areaChain[], point, access?: { trailhead, parking[] },
facts: Fact[] (value + provenance text), links: LinkGroup[], season, kidFit, photos: Photo[],
completeness: { level, passed, total, notTracked }, honesty[] }`;
`Photo { url, width, caption, author, licence, licenceUrl, sourceUrl }`.

### 2.5 Photos and credits

Every photo carries author and licence, and every screen that shows a photo renders the credits footer.
Gallery photos already have them. The 52 `locations.json` images are bare `Special:FilePath` URLs: LD fetches
their author and licence **once, sequentially**, with the Commons `imageinfo` API (50 titles per request, so two
requests), into the committed `web/data-snapshots/photo-credits.json`. Never run it from parallel agents
(the 429 of 12 Oct). A photo whose credit cannot be found is not shown; the kind glyph replaces it.

### 2.6 Completeness and honesty

- **Badge** from [research/kinds](../../research/kinds/README.md) section 10: "Draft", "Usable · 7 of 11",
  "Complete". The full engine is not built (TODO row "Enforce per-kind completeness"), so LD computes only the
  checks the data can answer (common D1 to D5, U1, U2, C1 to C4, plus each profile's U checks whose fields
  exist) and says so: the tooltip reads "7 of 11 tracked checks pass; 13 checks are not tracked yet". The
  function is pure and replaceable by the engine later.
- **Honesty markers** (dashed chips, components 2.8): Location unconfirmed, Unverified, No source yet,
  Dates open, Condensed from the full plan, Overview only, Drive time estimated (≈), 2026 data used as a
  pattern, and the trail data still waiting for a person (the Open TODO row: Braies P1, Monte Piana trailhead,
  three OSM routes, Viel dal Pan and Siusi figures, Lago d'Antorno about 500 m off) as "Location unconfirmed".

## 3. Maps

From [research/map-stack-2026-10-18.md](../../research/map-stack-2026-10-18.md):

| Surface | Map | Directions and distances |
|---|---|---|
| Globe, home cover, trip route map, Trips and Places map views | **MapLibre + OpenFreeMap + Mapterhorn** | trip legs: stored ORS values when present, else the estimate marked ≈ |
| Place and trail pages | **Google Maps JavaScript API** with our trailhead, parking and OSM line drawn on it, behind a feature flag; **Embed API** as the zero-cost fallback; **MapLibre until the key exists** | Directions = Google Maps URLs (and Apple Maps) to our stored points, no key |

The lanes never call MapLibre or Google directly, except the globe's own layers. Lane **LM** builds a map adapter
(`web/lib/map/`) with one `MapSurface` component and three families behind it. **A page declares one map family;
mounting a second family on the same page throws in development and fails the build test** (Google terms
3.2.3(e)). The Google key does not exist yet, so the place pages ship on MapLibre with
`NEXT_PUBLIC_PLACE_MAP_FAMILY=maplibre` (default); `google-js` and `google-embed` are wired, tested with a fake
loader, and switched on when the owner creates the key.

## 8. Gotchas

- **Static export and the globe drill-down.** `/globe/<cc>/<state>/<district>` must be pre-rendered:
  `generateStaticParams` from `globePaths()` (every path with content) plus a `/globe/*  /globe/  200` rewrite in
  `web/redirects.json` for any other path, read client-side from `location.pathname`.
- **`/globe/` collides with the legacy globe** in `tools/publish.py` (`SITE_ROUTES`). The tunnel preview serves
  `web/out` alone, so it does not matter until go-live.
- **The prototype data files import React** (`trails.ts` uses `useSyncExternalStore`, `trips.ts` the store), and
  their imports have no file extensions, so Node cannot import them directly. LD bundles them with the
  prototype's own `rolldown` and a React stub, then commits the JSON snapshot so `web` builds never need
  `prototype/node_modules`.
- **The prototype's Dolomites trip holds household data** (travellers and ages, booking codes, costs, phones,
  emails). LD snapshots it through an allow-list and the privacy test checks `web/out` for every such value.
- **Commons hotlinking.** The preview uses `Special:FilePath/<file>?width=<w>`. Production should cache
  thumbnails (R2 or a worker), as recommendation.md 7 says.
- **Drive times are estimates** (the prototype's straight line × 1.42; the Rockies' matrix INFERENCE). Show ≈ and
  the "Drive time estimated" marker until ORS values are stored at publish time.
- **Route lines.** No road geometry is stored yet. The trip map draws straight dashed segments between stops, and
  the legend says so ("straight lines between stops; road routes come later").
- **The `web/` green shell has tests that pin it** (no-hex, fonts, places-parity). L0 and L4 update them rather than
  delete them; a deleted test is a review failure.
