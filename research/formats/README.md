# Research output formats

Every format a research run writes, with its schema string, where it goes, the Zod file that defines it, how to validate it,
and a template or a real example. Records and sidecars go to `data/` (the system of record); only prose goes under
`research/`. The rules for what goes inside a value are in [../README.md](../README.md) section 9.

| Format | Schema string | Path | Defined in | Validate | Template or example |
|---|---|---|---|---|---|
| [Capture records](#capture-records-capture1) | `capture/1` | `data/capture/<trip-id>/<lane>.json` | `core/src/schema/capture/records.ts` (`capture`, `capRecord`) | `node core/bin/validate.ts <file>` | [templates/capture-record.json](templates/capture-record.json) |
| [Suitability sidecar](#suitability-and-relevance-sidecars) | `suitability/1` | `data/suitability/<trip-id>/<lane>.json` | `core/src/schema/suitability.ts` | `node core/bin/suitability.ts check` | `data/suitability/vermont-fall-2026/R6.json` |
| [Relevance sidecar](#suitability-and-relevance-sidecars) | `relevance/1` | `data/relevance/<trip-id>/<lane>.json` | `core/src/schema/relevance.ts` | `node core/bin/relevance.ts check` | `data/relevance/vermont-fall-2026/R6.json` |
| [Captured points](#captured-points) | `capture-points/1` | `data/capture/points.json` (one file) | no schema (`CapturedPoint` in `core/src/relevance/points.ts`) | the check below | [templates/capture-points.json](templates/capture-points.json) |
| Operators | `capture-operators/1` | `data/capture/operators.json` (one file) | `core/src/schema/capture/records.ts` (`operator`) | `node core/bin/validate.ts data/capture/operators.json` | the file itself |
| [Run record](#run-record-capture-run1) | `capture-run/1` | `data/capture/runs/<run-id>.json` | `core/src/schema/capture/records.ts` (`captureRun`) | `node core/bin/capture.ts run --check <file>` | [templates/capture-run.json](templates/capture-run.json) |
| Source registry | `sources/1` | `data/sources/registry.json` | `core/src/schema/sources.ts` | generated by `node core/bin/sources.ts build`; never hand-edit | - |
| [Inbox batch](#inbox-batch) | none | `research/inbox/<date>-<topic>.json` | the `import` command of `tools/locations.py` | `python3 tools/locations.py import <file>`, then `validate` | `research/inbox/2026-10-17-gulong-gorge.json` |
| [Lane findings](#lane-findings-markdown) | Markdown | `research/trips/<folder>/<lane>.md` | this page | none | below |

| [Trip file](#trip-file-tripjson) | `schema_version` 1 (no `schema` string) | `data/trips/<trip-id>/trip.json` | `core/src/schema/trip.ts`; contract [data/trips/README.md](../../data/trips/README.md) | `node core/bin/validate.ts <file>`; written only through `node core/bin/ops.ts` | [templates/trip.json](templates/trip.json) |

## Validating a template

`node core/bin/validate.ts` decides what a file is from its path before it reads the `schema` key, and it treats every JSON
file under `research/` as `research-sidecar/1`. A template validated in place therefore fails with a list of missing
`research-sidecar` columns. Validate a copy outside the repository; outside the repository layout the validator falls back to
the `schema` key:

```bash
T=$(mktemp -d)
cp research/formats/templates/capture-record.json research/formats/templates/capture-run.json research/formats/templates/trip.json "$T/"
node core/bin/validate.ts "$T/capture-record.json" "$T/capture-run.json" "$T/trip.json"   # OK: 3 file(s) validated
node core/bin/capture.ts run --check "$T/capture-run.json"                  # OK: 0 error(s), 0 warning(s)
rm -r "$T"
```

`capture-record.json` also prints `W_CAP_BELOW_USABLE` warnings, and `trip.json` prints `W_NO_COORDS` (its placeholder base has
no coordinates): a template shows the shape, not a complete record. Warnings never change the exit code.
`core/test/research/templates.test.ts` validates every template with `validateDoc` against its schema string (a trip file,
which has none, counts as `trip/<schema_version>`), so a schema change that breaks a template fails check-all (cleanup D16).

## Capture records (`capture/1`)

One file per trip and lane. The header names the run; `sources` is the table every value cites by id; `records` holds the
places, routes, offers and events.

| Key | Rule |
|---|---|
| `schema`, `trip`, `lane`, `researched`, `agent`, `model` | `capture/1`; the trip id (kebab case, for example `dolomites-2027`); the lane id; the date; who and which model |
| `sources[]` | `{id: "src-0001", url, title, publisher, kind, read, method, run?}`. `kind`: official, operator, reseller, press, blog, community, video, computed. `method`: read, crawl, api, computed, owner; `crawl` and `api` need `run` |
| `records[].ref` | resolves to a place, a legacy row or a trip item, or is cut out of one: `part/<parent ref>#<slug>` for a place, route or event inside it, `offer/<parent ref>#<product>` for a product sold at it |
| `records[].type`, `layer` | a type id of `data/vocab/types.json` and a layer the type allows (place, route, offer, event) |
| relations | `reaches`, `passes`, `part_of`, `starts_at`, `ends_at`, `on`, `at`, `run_by`, `parks_for`, `serves`, `combo_with`, `alternative_to`, `variant_of`. Never type `reached_by`; it is derived |
| values | `season`, `best_window`, `best_time`, `hours`, `duration_min`, `activity_min`, `price`, `window`, `book_url`, each wrapped as a value (below) |
| `links[]` | `{kind, url?, state, query?, on?, src?}`; `state` is `filled`, `searched_none` (with `query` and `on`) or `found_in_search` (link-only platforms) |
| `photos[]` | `{file, licence, author, attribution, source_url, width, height}` |

The value wrapper, on every value:

```json
{ "v": <value or null>, "state": "value | none_stated | searched_none | not_applicable | gap | no_limit",
  "basis": "operator_rule | operator_info | official_rule | official_grade | official_info | community | our_inference | null",
  "src": ["src-0001"], "read": "YYYY-MM-DD", "quote": "at most 300 characters", "note": "...",
  "tried": ["what was searched"], "on": "YYYY-MM-DD", "applies_to": "2026",
  "conflicts": [{ "v": <other value>, "basis": "...", "src": ["src-0002"], "note": "..." }] }
```

`v` is `null` unless `state` is `value`. A `searched_none` value lists `tried` and `on`. `our_inference` needs a `note` with
the method. Points do not go in a capture record; they go in `data/capture/points.json`.

The template holds one record of each layer, all cut out of `legacy/canadian-rockies-sept-2029/sights/moraine-lake` so its
refs resolve: a viewpoint (place), a walk that `starts_at` the shuttle stop and `reaches` the viewpoint (route), a canoe
rental `at` the lake (offer), and a larch peak `part_of` the lake with a recorded conflict (event). Replace every ref, URL and
value. What a type requires: `node core/bin/capture.ts fields --type <id>`.

## Suitability and relevance sidecars

They share the value wrapper and the `sources` table, join the capture records by `ref`, and carry `kind` and `subkind`.
Their records are large and depend on the kind, so the best template is a small real file: copy the shape of
`data/suitability/vermont-fall-2026/R6.json` and `data/relevance/vermont-fall-2026/R6.json`. The fields a ref needs:
`node core/bin/suitability.ts fields --ref <ref>`. Method: [../method/suitability.md](../method/suitability.md) and
[../method/relevance.md](../method/relevance.md). The `flat` block of a suitability record is computed (`suitability.ts derive`).

## Captured points

`data/capture/points.json` holds the points that research lanes read for capture records (OSM nodes and ways, Wikidata P625),
keyed by ref, plus corrections that beat the generic order of trust. `relevance.ts points --build` merges them into
`data/relevance/inputs/points.json`.

```json
"part/<parent ref>#<slug>": { "lat": 51.32000, "lon": -116.18000, "coord_src": "osm",
  "point_source": "OSM node <id> <name> (what the node is); read <date> (lane <id>); agent checked, needs a person's check" }
```

`coord_src` is `osm` or `wikidata` today; `official` and `manual` are the other honest values. No core validator reads this
file yet, so check a change with:

```bash
python3 -c '
import json,sys
d=json.load(open(sys.argv[1])); assert d["schema"]=="capture-points/1", "schema"
for ref,p in d["points"].items():
    assert set(p) <= {"lat","lon","coord_src","point_source"} and {"lat","lon","coord_src"} <= set(p), ref
    assert -90<=p["lat"]<=90 and -180<=p["lon"]<=180, ref
    assert p["coord_src"] in ("osm","wikidata","official","manual"), ref
    assert "google" not in json.dumps(p).lower(), ref
print("OK", len(d["points"]), "point(s)")' data/capture/points.json
```

## Run record (`capture-run/1`)

Every crawl or API run writes one, so the next pass starts where it stopped
([../method/capture-contract.md](../method/capture-contract.md) 9.6).

| Key | Rule |
|---|---|
| `run` | kebab case, `<lane or api>-<date>-<topic>`, for example `api-2026-10-19-cs7b-overpass` |
| `scope` | the `types` and `refs` the run covered; every result's ref must be in `scope.refs` when it is given |
| `hosts[]` | `{host, requests, robots, terms, status}`; a host whose robots or terms forbid automated access cannot report `ok` with requests |
| `results[]` | `{ref, field, outcome, src?, tried?, host?, reason?}`; `field` is a registry property; `filled` and `conflict` name `src`; `searched_none` lists `tried`; `blocked` names `host` and `reason` |

## Trip file (`trip.json`)

The trip itself, as data: no HTML and no PLAN.md for a new trip (owner, 21 Oct). The contract is
[data/trips/README.md](../../data/trips/README.md): the files per trip, the ids (a new trip id carries no year), the public
tables and the planner tables (the allowlist the web adapter reads), the dateless rules, the op sequence, validation and
what is not yet possible. Read it before writing a trip.

| Key | Rule |
|---|---|
| `schema_version`, `id`, `updated` | `1`; the trip id, equal to `trip.slug` and the folder name; the date of the last write |
| the 30 tables | always present and in `TRIP_TABLES` order (`E_KEY_ORDER`); a table with no rows is `[]`, `trip` and `profile` are objects |
| public tables | `trip`, `trip_tags`, `bases`, `days`, `day_tracks`, `items`, `trip_trails`, `trip_activities`, `custom_items`, `routes`, `hazards`, `weather_rules`, `knowledge`, `gotchas`, `sources`, each with a column allowlist |
| planner tables | `profile`, `travellers`, `editions`, `trip_bookings`, `notes`, `budget`, `fx`, `fare_windows`, `fare_quotes`, `documents`, `emergency`, `packing`, `questions`, `research_refs`, `changelog`. Empty in a public trip, except `profile` (required, neutral) and `changelog` (written by the ops) |
| writes | only through `node core/bin/ops.ts`: `trip.create`, `base.set`, `day.update`, `item.add`, then the rest (data/trips/README.md section 5) |

The template is a two-night, one-base public trip, built by running the op sequence of data/trips/README.md section 5.1
against a scratch copy of `data/`, so its bytes are exactly what the ops write. Its shape, with most columns of each row cut
(the file has every column):

```text
{
"schema_version": 1, "id": "example-trip", "updated": "2026-10-21",
"trip": {"slug":"example-trip","title":"Example trip","primary_style":"adventure","duration_shape":"weekend",
         "movement_shape":"single-base","party_shape":"couple","countries":["CA"],"season_months":[9,10],
         "season_note":"...","nights":2,"origin":"","origin_tz":"America/Toronto","web_published":false,
         "visibility":"public","legacy_url":null, ...},
"profile": { neutral defaults: required by trip.create, never public },
"travellers": [], "trip_tags": [{"tag_id":"adventure"}], "editions": [],
"bases": [{"id":"example-base","night_from":1,"nights":2,"tz":"America/Toronto","lat":null,"lon":null, ...}],
"days": [{"n":1,"kind":"travel", ...}, {"n":2,"kind":"hike","plan_b_title":"Rain plan", ...}, {"n":3, ...}],
"day_tracks": [],
"items": [{"id":"d1-checkin","day":1,"seq":1,"type":"checkin","base_id":"example-base", ...},
          {"id":"d2-viewpoint","day":2,"seq":1,"type":"sight","needs_daylight":true, ...},
          {"id":"d2-lunch","day":2,"seq":2,"type":"meal","optional":true, ...},
          {"id":"d3-checkout","day":3,"seq":1,"type":"checkout","start":"10:00", ...}],
"hazards": [1 row], "weather_rules": [1 row], "knowledge": [1 row], "gotchas": [1 row],
"sources": [], "changelog": [13 rows, one per op]
... every other table []
}
```

Replace every value. Gotchas the template already respects: `primary_style` must be `adventure` until the other style tags
exist, `countries` must be in the locations store, and every `src` stays `[]` because no op writes the trip's `sources`
(data/trips/README.md section 7, gaps 4 to 6). Items name no capture record yet; TD-1 adds that link.

## Inbox batch

Five or more places for the location store go in one file, `research/inbox/<date>-<topic>.json`, with the shape
`{"places": [spec, ...], "collections": [...]}`. A spec's keys match the flags of `locations.py add` (`name`, `country`,
`region`, `area`, `kind`, `lat`, `lon`, `tags`, `kid_fit`, `stats`, `notes`, `sources` with `type`, `url`, `note`,
`screenshot`, `post_date`). There is no dry run: `python3 tools/locations.py import <file>` writes the store, then the hook
validates and rebuilds. Real examples: `research/inbox/2026-10-17-gulong-gorge.json` (one place),
`research/inbox/2026-10-19-washington-road-trip.json` (a road trip).

## Lane findings (Markdown)

`research/trips/<folder>/<lane>.md`, one per lane, written by a lane agent as raw data for the planner, not as a report.

```markdown
# <Trip>: <lane>

Read <date>. Lane contract: research/method/lanes/<lane>.md.

## <Place or topic>
- Fact, with numbers and units. [source: <publisher>, <url>, read <date>]
- GAP: <field> not stated on <url>; <what else was tried>.
- Conflict: <source A> says X; <source B> says Y. Official value: X.

## Sources
- <publisher>: <url> (read <date>)
```

A later run that closes a gap writes `GAP CLOSED <date>` with the source on the same line, and says so when the new fact
contradicts the old note. Never delete a lane file; superseded plans go to `research/trips/<folder>/archive/`.

## Run note (Markdown)

`research/runs/<run-id>.md`, the prose companion of `data/capture/runs/<run-id>.json` (or of a lane file when there is no
run record). Sections: scope (trip, lane, types, refs), what was found, gaps and why, conflicts, questions for the owner,
the files written, and the commands run with their results.
